# 07: Flow shows the board while its first copy runs

**What to build:** the first time a board is connected, Flow shows its newest threads within a second, as ADR 0011 promises, and the rest of the board fills in above them while the copy runs. Today the window reads the replica only once the copy has finished, so a board of 100,000 messages leaves the sidebar and Flow empty for about 10 seconds, and a slower board for longer.

**Blocked by:** 06

**Status:** ready-for-agent

- [x] The copy stores the newest threads first: the first page of `GET /threads`, each root with its replies, before it replays the feed from the oldest message. Merging by `version` keeps the order of the two irrelevant.
- [x] The shell reads the replica while it is being copied, so Flow and the sidebar show what is stored and follow each stored batch, as they follow the live feed.
- [x] A copy that stops halfway, because the app quit or the board went away, is never taken for a whole one: the next start copies again or carries on, and says so.
- [x] Flow keeps to the bottom while older messages land above, and the count of new messages below counts none of them.
- [x] Tests come first: the order of the copy and a copy stopped halfway against the fake board; the count of new messages below against the fake core.
- [x] Verified by hand on the 100,000-message board, with its replica removed: the first rows appear within a second of the copy starting, the list stays at the bottom while the rest arrives, and the whole copy takes no more than a second longer than it does today.

## Comments

Built on 2026-11-21 by a subagent in its own worktree, test-first, on `main` at 2338cc3. The core gained 7 tests (4 in the reader, 1 in the replica, 2 in sync) and 5 were rewritten for the new replica files; the UI gained 9 (3 for the windows, 3 for the count of new messages below, 3 for keeping to the bottom).

**What was built.**

- **The copy stores the newest threads first.** It reads `GET /threads?limit=25`, then each of those threads whole with `GET /messages/:id?limit=500`, and stores them before anything else. Then it goes on as before: the older pages of `/threads` (each root and its latest reply, to find the oldest root), then the feed replayed from the oldest root. Merging by `version` makes the order irrelevant.
- **The shell reads the replica from that first batch on.** `copy_board` takes a callback for the moment the newest threads are stored, and `keep_in_step` announces the replica then rather than at the end. Every stored batch after that refreshes the reader, so Flow and the sidebar follow the copy as they follow the live feed.
- **A replica is whole once it has its feed cursor.** `Replica::finish_copy` writes the board's identity and the cursor in one transaction, at the end of the copy. On the next start, a replica without a cursor was stopped halfway: it is removed and the board is copied again, so the status bar says "Copying" from the first batch on. A whole copy of an empty board has a cursor and no identity, and is copied again on the next start, as before.
- **Replica files are named when the copy starts,** `<address>.<stamp>.sqlite`, made with `create_new`, because the shell now opens the file before the copy ends, and renaming an open SQLite file would part it from its `-wal` and `-shm`. Before, a copy ran in `<address>.new.sqlite` and was renamed after the board's oldest message when it ended. The identity now lives only in the `board` table. A replica named by `main` is still found, since it has the same prefix and schema. The schema did not change.
- **The reader places a batch of arrivals by sorting from the earliest one on** (`place_in_order`), instead of inserting each in turn: a batch of the copy can hold 9,000 older messages, landing in an ordered list of up to 100,000.
- **At the bottom, a change reads the end of Flow first and shows it with its new total at once** (`FlowWindows.renewTheEnd`). When older messages land above, every index moves, so the rows kept from before would sit at the wrong indices. While the end is read, the windows request nothing else and show what they had; an answer to a read made before is dropped.
- **The count of new messages below counts lines after the newest one the reader saw before leaving the bottom.** The core counts them (`count_flow_after`, `ReplicaReader::flow_lines_after_in`), so older messages, which land before that line, count for nothing. A fold that grew moves below it and counts as one.

Decisions made along the way:

- **The first page asks for 25 threads.** The 25 threads with the latest activity hold at least the newest 25 messages, more than a screen of lines, and on the 100,000-message board the copy announced its replica 250 ms after it started. A page of 500 would cost 500 thread reads before the first rows.
- **A copy stopped halfway is copied again rather than carried on.** Carrying on would mean keeping where the threads' pass and the replay had got to; copying again costs 16 s on the largest local board.
- **The shell refreshes the reader in a task of its own,** woken by a `Notify` after each stored batch, and refreshes coalesce when batches come faster. With the refresh inside the copy's task, the copy waited for the reader, and for its lock while the page read, and took 1.3 to 1.9 s longer than on `main` (loads 2.6 to 3.0), against the one second this ticket allows.
- **The list leaves the bottom only when the reader scrolls up.** In one run of eleven by hand, the list stopped following early in the copy and drifted up 187,466 px as older messages landed. Nothing was logged that explains it. It fits a line growing outside a React commit, for example when the fonts swap in, now that the first rows can be drawn 10 ms after the page starts: an animation frame after the list's own scroll then read it as away from the bottom. A person scrolling over the window as it appeared would leave the same trace. Either way, growth below no longer counts as leaving.
- **The tests of keeping to the bottom moved to `ui/flow/tests/scroll.tsx`,** beside `scroll.ts`, since `list.tsx`'s tests went over Biome's 300 lines. They now scroll up from where the list keeps to the bottom, as a reader does.

**Verified by hand** on the 100,000-message board (100,070 messages, 20 channels, 40 agent profiles), release build, the app run with its own `HOME` and an empty replicas folder. `main` was built from 2338cc3 with the same temporary harness and run alternately with this ticket's build:

| Round | `main`: whole copy | Load | This ticket: first rows | This ticket: whole copy | Load |
| --- | --- | --- | --- | --- | --- |
| 1 | 15.18 s | 2.66 | 258 ms | 16.02 s | 2.79 |
| 2 | 15.40 s | 2.61 | 271 ms | 16.15 s | 2.82 |
| 3 | 15.27 s | 2.49 | 258 ms | 15.99 s | 2.30 |

- On `main`, the first rows appear when the whole copy ends. Here they appear 258 to 271 ms after the copy starts, and the whole copy takes 0.72 to 0.84 s longer. Reading and storing the newest threads take about 0.25 s of that. The rest is the page and the reader working alongside the copy, and was not broken down further: the 505 refreshes, now off the copy's path, took about 0.5 s in all, 12 ms at most.
- **At the bottom,** every frame of the three runs was sampled (2,130 to 2,147 frames each): the list never left the bottom, its bottom row was never blank, and that row stayed the board's newest message throughout.
- **Scrolled up** 3,000 px, 3 s after the first rows (load 2.87): no notice of new messages below in any of the 1,742 frames until 2 s after the copy ended, while older messages landed above.
- **The app quit halfway** (load 2.45): stopped 4 s into the copy, the replica held 32,914 messages, no feed cursor and no identity. The next start (load 2.29) removed it, read "Copying 25 of 100,070" with its first rows, and ended with one replica of 100,070 messages, its cursor and its identity, 16.5 s later.
- **The board went away halfway** (load 1.98), on a `vb serve` of the subagent's own on port 4300 with 20,000 messages: stopped right after the first rows, it left a replica of 2,533 messages with no cursor. When it was started again, the app began a new copy 6.9 s after the board had stopped, into a new replica, and went live with all 20,000 in 1.7 s; the half copy was gone.
- **With the replica there** (load 2.45), the first rows came 59 ms after the page started. Scrolling at 120 Hz: 359 of 360 frames on time at 2,000 px/s (worst 13 ms), 359 of 360 at 8,000 px/s (worst 14 ms), 361 of 361 at 30,000 px/s (worst 11 ms), with no blank row. Jumps to five depths filled within 7 ms. Afterwards the app's process had a footprint of 55 MB and WebContent 100 MB, as in Flow 04.
- **A replica `main` made** is found and followed with no new copy (load 1.37): the first rows came 55 ms after the page started, and the folder kept its one file.
- The replica file is 141.6 MB, against 141.5 MB on `main`.

Left for later:

- **Scrolled up while a copy runs, the reader's place is not held.** Older messages land above and the rows under the reader move: in the run above, the top row went from message 99418 to message 25048. Holding it needs the core to say where a line sits now, which is a new request. It happens only while older messages arrive: the first copy, or a message that lands late with an older time.
