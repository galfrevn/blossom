# 08: Flow follows what changes about a message after it is stored

**What to build:** the open reader catches up with every change to what the replica stored about a message, not only with new messages. A thread made into a task after its replies arrived (`vb tasks create <id>`) turns its agents' replies into progress, and they fold. An edit that adds a mention takes its reply out of a fold, and one that removes it brings the reply back in. Today the reader catches up only from the messages that arrive, so these changes appear only when it opens again (found in Flow 04).

**Blocked by:** 04, 07, Thread 01, Tasks 02

**Status:** ready-for-agent

- [ ] The replica logs, in the transaction that stores them, every change to a stored message's facts (its `re`, its author, whether it is progress) and every thread that becomes a task. The reader reads that log as it reads the messages that arrive.
- [ ] The open reader catches up from that log without opening again: a thread made into a task folds the progress already in it, and an edit that adds or removes a mention moves its reply out of or into a fold.
- [ ] Catching up with one such change costs what catching up with one arrival costs today on the 100,000-message replica (0.6 to 2.4 ms in Flow 04), measured and written in the comments.
- [ ] Tests come first, against a real SQLite replica: a task made from a thread that already has agents' replies, an edit that adds a mention, and one that removes it.
- [ ] Verified by hand on `vb serve`: in the open app, `vb tasks create <id>` on a thread with agents' replies folds them, and editing one of them to add a mention takes it out of the fold.

The replica already keeps two logs that are never trimmed: `arrivals` (Flow 03) and `task_changes` (Tasks 02). This ticket adds a third reason to read a log. If keeping them small on a board of 100,000 messages needs a decision, it goes in the comments for an ADR.
