# 08: Flow follows what changes about a message after it is stored

**What to build:** the open reader catches up with every change to what the replica stored about a message, not only with new messages. A thread made into a task after its replies arrived (`vb tasks create <id>`) turns its agents' replies into progress, and they fold. An edit that adds a mention takes its reply out of a fold, and one that removes it brings the reply back in. Today the reader catches up only from the messages that arrive, so these changes appear only when it opens again (found in Flow 04).

**Blocked by:** 04, 07, Thread 01, Tasks 02

**Status:** ready-for-agent

- [x] The replica logs, in the transaction that stores them, every change to a stored message's facts (its `re`, its author, whether it is progress) and every thread that becomes a task. The reader reads that log as it reads the messages that arrive.
- [x] The open reader catches up from that log without opening again: a thread made into a task folds the progress already in it, and an edit that adds or removes a mention moves its reply out of or into a fold.
- [x] Catching up with one such change costs what catching up with one arrival costs today on the 100,000-message replica (0.6 to 2.4 ms in Flow 04), measured and written in the comments.
- [x] Tests come first, against a real SQLite replica: a task made from a thread that already has agents' replies, an edit that adds a mention, and one that removes it.
- [x] Verified by hand on `vb serve`: in the open app, `vb tasks create <id>` on a thread with agents' replies folds them, and editing one of them to add a mention takes it out of the fold.

The replica already keeps two logs that are never trimmed: `arrivals` (Flow 03) and `task_changes` (Tasks 02). This ticket adds a third reason to read a log. If keeping them small on a board of 100,000 messages needs a decision, it goes in the comments for an ADR.

## Comments

Built on 2026-11-21 by a subagent in its own worktree, test-first, on main at c1f687b. The reader's suite gained 5 tests. Four failed first: a thread made into a task with agents' replies already in it, progress stored before its task, an edit that adds a mention, and one that removes it. The fifth guards that an edit changing none of a message's facts moves nothing.

**What was built.**
- **A third log, `message_changes`,** kept by two triggers in the transaction that stores the views:
  - an update of a stored message that changes its channel, `re`, author or whether it is a plain agent reply logs the message. An edit of its text alone logs nothing;
  - a new task logs the replies already in its thread, found through `messages_by_thread`.
- **The reader reads `arrivals` and `message_changes` in one snapshot.** It places what arrived, puts each changed message's facts back in its place in the order (Board never changes a message's `createdAt`), and builds the lines again only when a fact the lines use moved.
- **The lines are built without hashing:** the fold growing in each channel is kept in a vector indexed by the channel's number, where a `HashMap` stood. That halved every catch-up, arrivals included.
- **The schema is version 7,** so a replica from before is copied again. The shell needed no change: it already catches the reader up and announces a Flow change after every batch.

**Decisions made along the way:**
- **A log of its own, not `task_changes`.** `task_changes` logs every insert and update of a task, about 1.6 rows per task event plus one per task: 28,020 rows for the 10,000 tasks and 17,898 events of Tasks 02's board. It does not say which tasks are new, so reading it for Flow would re-read a thread at every claim and renewal.
- **A new task logs its replies, not its root,** so the reader catches up with one query, as it does from `arrivals`. This also folds the progress a copy stores before its task, which the reader had read as plain replies.
- **Only real changes are logged.** A view delivered again, or an edit of the text alone, writes nothing to the log, and the window shows the new text as it reads each row.

**Measured** on a replica of the shared board, copied by the release build under a home of its own: 100,070 messages, 95,407 of them agents' replies in 4,393 threads, none a task. The copy took about 17 s and logged nothing in `message_changes`. A temporary program, not in this change, timed `catch_up` on a copy of that file, 30 times for each case, twice.

| Catching up with | Few threads are tasks | Every thread is a task |
| --- | --- | --- |
| one arrival | 0.29 ms (0.65 ms before the lines change) | 0.93 to 0.95 ms (1.9 to 2.1 ms before) |
| an edit that adds a mention | 0.38 to 0.39 ms | 1.00 to 1.01 ms |
| an edit that removes it | 0.36 to 0.37 ms | 0.93 to 0.96 ms |
| a thread made into a task, 12 to 79 replies (50 at the median) | 0.64 to 0.66 ms, worst 0.88 ms | |

- **Load average** 3.2 for the table. Before the lines change, at 3.6 to 3.9, an edit cost 2.4 to 2.7 ms with every thread a task. Reading the log and putting the message back took 15 to 30 µs of that, and the rest was building the lines again.
- **Storing** an edit took 0.09 ms at the median, and a thread made into a task 0.32 to 0.36 ms.
- **Making the other 4,363 threads tasks in one batch** stored in 0.92 to 0.97 s and logged 93,951 replies. The reader caught up with all of them in 352 to 384 ms.
- **Opening the reader** took 28 ms with no thread a task and 62 to 63 ms with every thread one (Flow 04: 31 and 51 ms).

**Verified by hand** against `vb serve` 0.54.0, with the release build under a home of its own and Flow open throughout:
- A thread in `#fleet/www` held four replies by `claude` and `codex`, each a line of its own.
- `vb tasks create 3` folded them, within the 2 seconds before the picture, into "#fleet/www · 4 progress updates from 2 agents · latest: deploying to production".
- `vb edit 7 "… @galfrevn which ones matter?" --as codex` took the reply out: one update, the edited reply, then two updates.
- Editing the mention away brought it back into a fold of four.
- The replica's `message_changes` held exactly six rows: the four replies when the thread became a task, then reply 7 once for each edit.

**For an ADR: keeping the logs small.** All three logs grow forever on a board of 100,000 messages:
- `arrivals` holds one row per message, about 100,000 rows. It is also the full-text index's rowid for each message, so it cannot be trimmed as it stands. `messages` has no rowid of its own.
- `task_changes` holds about 1.6 rows per task event.
- `message_changes` holds one row per edit that changes a fact, and one per reply of a thread made into a task: none for the copy of this board, 93,951 had every thread become a task at once.

The reader needs only the rows after its cursor, and it lives in the same process as the writer. So the writer could delete the rows of `task_changes` and `message_changes` that the reader has read. Trimming `arrivals` would first need the full-text index keyed by something else. Whether and when to trim is for the owner.

Seen along the way, for a later ticket: a mention in a Flow line reads as its stored form, `@[local:user:galfrevn]`.
