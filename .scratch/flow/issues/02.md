# 02: Flow reads the whole board in windows

**What to build:** Flow lists every message on the board oldest first, opened at the newest, with a divider for each minute. Each line shows its time, its author and the person it acts for, its channel and its text. The UI asks the core for windows and draws only what is near the screen, so 100,000 messages scroll without a stutter.

**Blocked by:** 01

**Status:** ready-for-agent

- [x] The core keeps the ordered sequence of messages (creation time, then ID) for the open board, built when the replica opens, and answers windows of it by ID, never with `OFFSET`.
- [x] The contract gains the request for a window, `{ total, start, items }`, and a subscription that announces a changed total.
- [x] The list measures rows as it draws them, keeps a running total of heights in a Fenwick tree, draws 600 px beyond each edge, and holds only the windows near the screen.
- [x] Minute dividers are drawn above the first message of each minute.
- [x] Tests come first: windows at any depth and the minute dividers in the core; the list's arithmetic on its own; the drawn rows against the fake core.
- [x] Verified by hand against the 100,000-message board: it opens at the newest, a jump anywhere fills in under 50 ms, no row shows blank at 30,000 px/s, and idle memory stays under 150 MB across the app's processes, measured as `documentation/research/list.md` did.

## Comments

Built on 2026-11-21. The core gained 7 tests (the reader's flow), and the UI 13 (row heights 7, the window cache 4, Flow's lines 6, minus the ones moved).

**Measured by hand** against `vb serve` holding 100,065 messages, with a measuring harness on a throwaway worktree, never committed:

- **Opening:** at the newest message, with the first rows 335 to 355 ms after launch.
- **Frames at 120 Hz:** 358 to 359 of 360 on time at 2,000 px/s, 354 to 359 at 8,000, and 350 to 352 at 30,000. No row was ever blank.
- **A jump anywhere:** filled in 17 ms at the median and 25 ms at worst.
- **Idle memory, nothing scrolled:** 126 MB across the app's four processes (the app 45, WebContent 62, GPU 14, networking 5).

Decisions made along the way:

- **The reader keeps the flow's order in memory:** the creation time and ID of every message, built when it opens. A trigger writes each new message's ID into an `arrivals` table, and the reader catches up from the last arrival it saw, inserting late messages in their place. The write path is untouched.
- **A minute's divider lives in the first message of that minute** (`firstOfItsMinute`), so every position in the sequence is a message and windows never shift around dividers.
- **Rows are placed with transforms, not between spacers.** With spacers, every frame laid out the whole column, and 30,000 px/s kept only 90% of frames on time.
- **Each row is measured once,** until the board changes or the list's width does. Each `offsetHeight` read forces a layout.
- **Rows are memoized,** since a window's rows stay the same objects between frames.
- **The UI keeps 30 blocks of 100 rows** and lets go of the oldest.
- **`startsAMinute` became `firstOfItsMinute`:** the naming rule refuses two capitals in a row.
