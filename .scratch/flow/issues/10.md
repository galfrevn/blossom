# 10: Mentions read as names, and Flow's lines as plain text

**What to build:** a mention reads as the name of whom it mentions, `@claude`, in Flow's lines and in the thread pane, not as its stored form `@[local:user:galfrevn+claude]`. Flow's lines show a message's text as plain text: the markdown's marks go, its words stay, and a line keeps to one or two lines as it does today. The pane keeps rendering markdown (Thread 02).

**Blocked by:** 07, Thread 02

**Status:** ready-for-agent

- [x] A mention of an actor the replica knows reads as its name, and one it does not know as the ID without its brackets. A mention is never a link.
- [x] Flow's line drops headings' hashes, emphasis marks, fences and link targets, and keeps the text they hold, with no markdown parsed on the row's hot path beyond what the budget allows.
- [x] Search's snippets read mentions the same way.
- [x] Tests come first: mentions with known and unknown actors, and each markdown construct in a line.
- [x] `bun run check` passes, with the JavaScript budget.

**What was built.**

- **The core names who a text mentions.** A Flow row and a thread message carry `mentions`: the ID and the name of each actor their text mentions that the replica knows. Unknown actors are left out, and a deleted message carries none. The contract gained `MentionedActor`. `core/src/reader/mentions.rs` finds `@[id]` in a text and looks each ID up in `actors`, once per message.
- **The UI reads a mention with marked's lexer.** It adds an inline tokenizer for `@[id]` (`ui/markdown/mention.ts`), built for each message from its names. A mention becomes its own token, `@name`, or `@id` when the replica does not know the actor. The lexer tries its own extensions before links and bare addresses, so a mention is never a link:
  - `@[id](url)` reads as the name and then the text in brackets;
  - `[id]: url` defines nothing it can use;
  - `@[ada@vercel.com]` is not a mail address.

  Inside code a mention reads as written, as Board counts no mention there. In the pane it is drawn as the concept draws a mention in Attention, in medium weight and the accent's ink, and never as an anchor. The lexer moved from `blocks.tsx` to `ui/markdown/lexer.ts`, so the pane and Flow's lines read a message the same way.
- **A Flow line is the message's plain text** (`ui/markdown/plain.ts`, used by `textOf`, so a fold's latest line and its recent lines are plain too). The same tokens are flattened to their words:
  - headings lose their hashes, and emphasis, strong emphasis and strikethrough lose their marks;
  - inline code and fenced or indented blocks keep only their text;
  - a link keeps its text, and an image its description;
  - a quote, a list item and a table row are each a line, with a table's cells apart by a space;
  - raw HTML reads as the text it is, as in the pane.
- **Search's snippets read mentions the same way.** The core rewrites each snippet of a message or a task with the names it knows. A mention whose words matched is marked whole, `@claude`. A snippet that FTS5 cut inside a mention reads that mention whole. FTS5 does this at either end: `…ada+claude] deploy` and `ask @[local:user:ada+claude…` both came out of the snippets the 100,000-message board would show. The core finds where the snippet sits in the message's text, takes every mention it overlaps, and keeps the ellipses. A snippet that overlaps no mention comes out as before.

Decisions made along the way:

- **The core sends names, the UI writes the mention.** The core could not rewrite the text itself. Markdown would then read the name as text: `@ada@vercel.com` would turn into a mail link, and a name holding `*` into emphasis. A row's list of names is usually empty.
- **A Flow line reads at most the first 1,000 characters.** That is well beyond the four lines a line shows, and it bounds the lexer on the row's hot path. In Bun, which runs JavaScriptCore as the webview does (load 4.4), a line's text took:
  - 3.3 µs for a progress line;
  - 25 µs for a report of 250 characters;
  - 89 to 96 µs for a report of 1,000 characters or more.

  Lexing a whole message of 10,000 characters took 0.8 ms (load 2.7): forty such lines read again after a change would have taken 32 ms. When a message is cut, it is cut at a space and the line ends with "…". Only a fold's opened lines, which have no clamp, could show that end.
- **Blocks are lines, and the clamp stays at four lines, as today.** A blank line between paragraphs no longer takes a line, so a report shows more of itself in the same height, and no line grows. If the owner wants every line held to one or two lines, that is the clamp's one class. Running blocks together with spaces was tried in thought and left: a heading and a list then read as one run-on sentence.
- **No memory of lines read.** A screen of forty lines is read again in about 1 ms after a change, and in 4 ms if every line is 1,000 characters or more.
- **Snippets are not read as markdown,** as before: they show the stored text with only its mentions rewritten. A mention typed inside code therefore reads as a name in a snippet, and as written in the pane and in Flow.
- **An actor the replica has never met reads by its ID.** The replica learns actors from the messages they write, their tasks and the feed's bookkeeping, not from being mentioned. Fetching mentioned actors from the board would be a change to the copy, and was left alone.
