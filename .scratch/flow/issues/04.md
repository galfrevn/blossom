# 04: Progress folds into one line per channel

**What to build:** a run of agents' progress messages in a channel folds into one line: "#channel · 12 progress updates from 3 agents · latest: …". Opening the line shows its last messages in place. Anything that is not progress in that channel closes the fold.

**Blocked by:** 03

**Status:** ready-for-agent

- [x] The core folds over the sequence: a progress message is a reply in a task's thread, by an agent, with no mention, no attachment and no task change; a channel's fold grows until something else happens in that channel.
- [x] A fold sits where its latest message sits, and a growing fold moves to the bottom.
- [x] The fold's line reads as the concept draws it, and opens in place to show its last eight messages.
- [x] Tests come first: each folding rule in the core, and the open and closed fold in the UI.
- [x] Verified by hand on a board where several agents post progress in tasks' threads.

## Comments

**Verified by hand** against `vb serve` with two tasks, agents' replies under two profiles, a person's reply and messages in another channel:

- Flow read "#fleet/www · 5 progress updates from 1 agent · latest: …", then "#fleet/api · 2 progress updates from 1 agent", then the person's reply, which closed the first fold, then "#fleet/www · 3 progress updates from 2 agents".
- Opening a fold showed its messages in place. The lines below moved down, and no two rows overlapped, before or after.

Decisions made along the way:

- **The rule.** A progress message is a reply whose root is a task, written by an agent, with no mention (`@[` in its text) and no attachment. Task changes are events on the root, never replies, so "no task change" holds by itself.
- **The facts are stored when a view is written.** Each message keeps its `re`, its author's actor ID and whether it is a plain agent reply, and the ordering index covers them, so the reader reads the order from the index alone. Reading the same facts from the JSON views took 250 to 280 ms, because SQLite parses each view, and stored generated columns keep SQLite from treating the index as covering. The schema is version 2, so a replica from version 1 is copied again.
- **The reader reads each row straight into the order,** without an intermediate string per row. Collecting 100,000 rows first left about 18 MB more in the app's footprint after they were freed.
- **The lines are built in one pass from the newest message back,** so a fold is placed at its latest member when it is first seen.
- **A fold carries its last eight messages,** and the UI keeps whether it is open.
- **A fold's agents are counted by actor ID.**
- **Opening a fold changes its row's height,** so the list watches the size of each row on screen and measures again a row whose height changed. It watches only the rows on screen and lets go of the ones that leave.
- **The minute divider is a heading of its own** above any line, a fold too.
- **A deleted update reads as deleted** in the fold's line and inside it.

Left for the next change, which needs Thread 01's index on threads:

- A thread made into a task after its replies arrived (`vb tasks create <id>`), and an edit that adds or removes a mention, change the stored facts. The open reader does not see them until it opens again. It is ticket 08.
