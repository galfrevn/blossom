# 09: Flow holds the reader's place while the first copy lands above

**What to build:** scrolled up during a board's first copy, the line the reader is looking at stays where it is on screen while older messages land above it. Today the rows under the reader move: in one run of Flow 07 the top row went from message 99418 to message 25048 while the copy ran.

**Blocked by:** 07

**Status:** ready-for-agent

- [x] The core answers where a line sits now in the narrowed order, by the line's message, so the UI can find its anchor again after a change.
- [x] After each change, a list that is not at the bottom keeps its anchor line at the same height on screen, and the count of new messages below still counts only what landed below it.
- [x] Tests come first: the position of a line after older messages land, in the core; the anchor kept through a change, against the fake core.
- [x] Verified by hand on the 100,000-message board with its replica removed: scrolled up during the copy, the line on screen stays put until the copy ends, and the frames hold while it does.

## Comments

Built on 2026-11-23 by a subagent in its own worktree, test-first, on `main` at cb7e811. The core's reader gained 3 tests. The UI gained 9:
- 2 for the windows;
- 4 for reading the rows around a line held, in `ui/core/tests/places.ts`;
- 3 for the list, in `ui/flow/tests/place.tsx`.

Every test was written before the code it specifies. The core's 3 failed to compile without the new request. The list's 3, and the windows' 2 run against `main`'s windows, were seen failing.

**What was built.**

- **The core counts the lines before a message** (`ReplicaReader::flow_lines_before_in`, the shell's `count_flow_before`), in the whole Flow or in a narrowed one. That count is the index of the line the message ends, so it says where that line sits now. It shares one split of the lines with `flow_lines_after_in`, the count of new messages below, so the two can never disagree about where a line falls. It costs two binary searches, plus the narrowed lines that are already kept for each revision.
- **The windows read the rows around a line held** (`Windows.renewAround`). They ask the core where the line sits, read the blocks around it, and show them with the new total at once. While they read, they ask for nothing else and keep showing what they had, as at the end (Flow 07). Reading the end and reading a line held now share one state, so a change at the end that comes while a line is read is read once the line is shown. Reading a place, the end or a line, moved to `ui/core/places.ts`; the windows keep the blocks.
- **The line held is found in the rows that were read,** not taken from the count alone. The count and the rows are separate requests, and the replica can change between them: a fold that grows moves every line after it by one, and leaves the total as it was. So the rows are taken only when every read agrees on the total and holds the line together with the row before it. When they do not, the windows ask again.
- **Away from the bottom, each change holds the first line that starts on screen** (`ui/flow/place.ts`). Once it is found, the list puts it back at the same height on screen: the scroll moves by what landed above. The count of new messages below is unchanged and still counts only the lines after the newest one seen.
- **A change that comes while the line is being found waits for it.** The list then holds a line again from where the first was found. A line picked earlier would carry its index from before the move, and land as many lines away as had arrived.
- **Rows measured again after a change no longer move the line.** The third test of the list found the problem. The list compared each row's top, already moved by the rows measured before it, with the screen's top from before any of them. So a row just above the screen could count as one below it. The list now compares with where the screen's top has moved to. The problem was older than this ticket: in the test, ten lines above the screen that measured taller than estimated left the line 230 px lower than it should have been, without any change at all.

Decisions made along the way:

- **The line held is the first one that starts on screen,** not the one the top edge of the screen cuts. A line's own height changes when it is measured again, and only a line that starts on screen stays put through that.
- **The place is found by order, not by identity.** The count of lines before a message gives the line that now sits where the held one sat in time. A fold that grows moves to the bottom (Flow 03). The reader keeps their place in time, and is not taken down with the fold (`a_fold_that_grew_away_leaves_its_place_to_the_line_that_came_after_it`).
- **The windows drop every other block when they show a line held,** as they do when they show the end. After older lines land, those blocks sit at the wrong indices.
- **The heights of lines above the drawn rows stay where they were by index.** Only their sum moves, and the list puts the line held back by that sum, so nothing on screen moves. Shifting them with the lines would mean knowing where each new line landed.
- **No line loaded on screen, no line held:** the list renews its rows as before. Mid-copy, the rows on screen are always loaded, since showing a held line loads the blocks around it.

**Verified by hand** on the 100,000-message board (100,070 messages), release build, the app run with its own `HOME` and an empty replicas folder before each round. A temporary harness in the page, removed before handing over, did the following:
- 3 s after the first rows, it scrolled up 3,000 px, as in Flow 07;
- half a second later, it held the first line that started on screen;
- on every frame, and every 100 ms, it read that line's height on screen, until 2 s after the status bar stopped saying "Copying".

| Round | Load before / after | First rows | Line held, index then → when the copy ended | Moved on screen | Frames, late, worst | Copy ended after scrolling up |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 5.46 / 5.87 | 368 ms | 100101, 23,545 → 100,059 | 0 px in 1,877 checks | 1,733 frames, 2 over 12.5 ms, worst 27.0 ms | 12.95 s |
| 2 | 5.87 / 5.25 | 370 ms | 100037, 26,350 → 99,996 | 0 px in 1,920 checks | 1,773 frames, 3 over 12.5 ms, worst 16.0 ms | 13.27 s |

- **Through both copies, the line held never moved,** while its index moved 408 to 423 times and grew by about 75,000 as the replay landed older messages above it.
- **Something was always on screen.** In every check a loaded line started on screen, and no notice of new messages below appeared.
- **The frames held.** The median frame was 8.0 ms, at 120 Hz. In round 1 one frame took longer than 16.7 ms; in round 2 none did.
- **The window has to be visible for these numbers.** A covered WKWebView reports itself hidden and draws no frames, so for the measuring rounds the harness kept the window above the others, small and in a corner. Before that, two runs drew nothing behind other windows. Of the runs with the window on top, one went hidden partway. Three ended before their copy did: twice the window was asked to close from outside the app, once before a line was held and once after; once, before the harness logged closing, the app was simply gone. None of these is in the table. No third clean round was tried, so as not to put the window up again on a screen that someone was using.

Left for later:

- **A line taller than the screen** has no line starting on screen until its end, so the line held is the one after it, below the screen. If older messages land between the two during a copy, the tall line moves. It takes a fold opened taller than the window, during a copy or with a message that arrives late.
