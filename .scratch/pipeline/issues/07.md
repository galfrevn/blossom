# 07: Every job has a time budget that fails it

**What to build:** each job has a budget for its checks and fails when a warm run exceeds it, so CI cannot slow down without someone noticing. Every run prints each job's time against its budget, as `budgets.sh` already does for sizes.

**Blocked by:** 02

**Status:** ready-for-agent

- [x] Budgets come from the runs measured after tickets 01 and 02, with the margin written down. Starting points: Linux 60 s, `desktop` 60 s, `installer` 120 s.
- [x] `budgets.sh` gains a mode that measures a job's time from its first step and compares it with the budget. It prints the result in the job summary on every run, passing or not.
- [x] A warm run, meaning the Rust cache matched in full, fails when it exceeds its budget.
- [x] A cold run is reported as cold. It is capped by the job's `timeout-minutes`, set from the slowest cold run measured (380 s on macOS today) and never raised to make a run pass.
- [ ] Proven. A budget of one second fails the job, locally through `budgets.sh` and once in CI on a branch. It is not committed.
- [x] ADR 0021 lists the budgets.

## Notes

- No retries, no wider timeouts, no skipped tests. A job that needs a retry has a bug, and the bug is found.
- A cold run is not a failure of the code. Failing it would leave the cache unwritten, and `main` would stay red after every toolchain bump.

## Comments

- **How it works, 2026-11-20.** Each job's first step writes `JOB_STARTED_AT` to `$GITHUB_ENV`. The last step runs `sh budgets.sh time <job> <seconds>`, with `RUST_CACHE_FULL_MATCH` set from the `cache-hit` output that `.github/actions/rust` now passes on from `rust-cache`. The script prints `<job>: <elapsed> s of <budget> s, warm` or `…, cold, the rust cache did not match in full` to the log and to the job summary. It fails only a warm run over its budget. The time covers the job's own steps, from the first to the last check. It leaves out GitHub's setup and the cache save in the post steps.
- **Warm runs measured, the whole job.**
  - Linux, with zizmor and cargo-deny: 43 s (run 44846799562, `b790511`) and 49 s (run 44846933713, `0b1fe47`). Before ticket 06 it took 28–36 s.
  - `installer`: 78 s on a documentation push (`b790511`) and 112 s when `Tauri.toml` changed, which rebuilt the shell in release (`0b1fe47`).
  - `desktop`: no warm run yet. Its cache was first written by `0b1fe47`, the first green run of the split job.
- **Budgets: about 1.3 times the slowest warm run, rounded up to 10 s.** Linux 49 s gives 70 s, and the installer's 112 s gives 150 s. `desktop` keeps the plan's starting point of 60 s. Before the split, Clippy took 12 s warm inside the old macOS job, and setting up the job takes about 15 s. The run of this ticket's own push is the first warm `desktop` run, and it confirms or corrects that figure.
- **Timeouts: about 1.5 times the slowest cold run, rounded up to whole minutes.**
  - Linux: 108 s, run 44846020839, so 3 min.
  - `desktop`: 95 s (run 44846933713), and 105 s in run 44846210752, which failed on the missing license. So 3 min.
  - `installer`: 301 s, run 44846210752, so 8 min.

  The old combined macOS job took 388 s cold, and no job takes that long any more.
- **Proven locally.** `JOB_STARTED_AT` five seconds back, a budget of 1 s and `RUST_CACHE_FULL_MATCH=true` exits 1 with `linux is over its time budget`. The same run reported cold exits 0. A 60 s budget passes. Without `JOB_STARTED_AT` it exits 2. The summary file received one line per run.
- **Still to prove in CI:** a 1 s budget failing a job. The workflow runs on pushes to `main` and on pull requests, so this needs a throwaway pull request from a branch, which reads the cache and never writes it. Opening one is the owner's call.
