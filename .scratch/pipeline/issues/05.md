# 05: The UI's tests run in random order

**What to build:** Vitest shuffles the order of the UI's tests on every run and prints the seed, so a test that only passes after another one fails sooner rather than later, and the failure can be replayed.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [x] Vitest's configuration shuffles files and tests (`sequence.shuffle`).
- [x] A failing run prints the seed, and passing that seed back reproduces the order.
- [x] Proven. Two tests that share state through a module-level variable fail in some order, and the seed of that order reproduces the failure. They are not committed.
- [x] The comments below record the UI tests' time before and after.

## Notes

- `isolate: false`, sharding and one database per shard are not adopted. There is one test file, it runs in 1 s, and the core's tests each use their own temporary directory. Revisit when the UI's tests pass 30 s.
- The core's tests already run in parallel threads. Rust's shuffle flag needs a nightly toolchain, which the project does not use.

## Comments

- **Done on 2026-11-20 with Vitest 5.1.1.** `ui/vite.ts` sets `sequence.shuffle: true`, which shuffles both files and tests. Vitest prints `Running tests with seed "<seed>"` under its banner on every run, passing or not, so a failure in CI already carries its seed. `bun run --cwd ui test -- --sequence.seed=<seed>` replays that order.
- **Proven.** Two throwaway tests in one file pushed their names into a shared module-level array and expected the order `first`, `second`. Of eight runs, seed `1795220672382` failed both tests. Passing that seed back failed the same two tests three times out of three, and seed `1795220670286` passed. The files were deleted and are not committed.
- **Time, three runs each on a warm machine.** Before: 227–231 ms in Vitest, 0.39–0.40 s wall clock. After: 227–252 ms, 0.39–0.45 s. No measurable change.
