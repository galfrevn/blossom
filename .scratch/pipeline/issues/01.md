# 01: The Rust cache hits

**What to build:** a push that changes no Rust dependency and no toolchain restores its Rust cache with a full match, on Linux and on macOS, whatever runner image GitHub hands out. Caches are written only by pushes to `main`. Pull requests read them and never write their own. ADR 0021 records how CI works.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [ ] The pinned toolchain is written once in `ci.yml`, as a workflow-level variable that both the toolchain step and the cache key read.
- [ ] `Swatinem/rust-cache` stops hashing the runner's installed toolchains (`add-rust-environment-hash-key: false`). The pinned toolchain version goes into its key instead, so a toolchain bump still starts a new cache.
- [ ] The cache is saved only on `refs/heads/main` (`save-if`).
- [ ] Proven both ways. A push that changes only documentation restores with `full match: true` on both jobs. A push that bumps the toolchain misses, as it must.
- [ ] ADR 0021 records how CI works: free standard runners, pushes straight to `main`, the full suite on every push with no selection, a newer push cancels an older run, the pre-push hook as the gate, and the time budgets. Each decision carries its reason from the spec. `documentation/README.md` gains its row.
- [ ] The comments below record before and after by run ID: cache hits and the time of each job.

## Notes

- The image rollout that broke the key is in the spec: run 44829533423, attempt 1 on image `20261102` and attempt 2 on `20261117`, with keys `688f0a87` and `60948658` for the same commit.
- `CARGO_INCREMENTAL=0` stays as `rust-cache` sets it. Incremental artifacts would make the cache larger without speeding up a clean CI build.
