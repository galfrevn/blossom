# 01: The Rust cache hits

**What to build:** a push that changes no Rust dependency and no toolchain restores its Rust cache with a full match, on Linux and on macOS, whatever runner image GitHub hands out. Caches are written only by pushes to `main`. Pull requests read them and never write their own. ADR 0021 records how CI works.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [x] The pinned toolchain is written once in `ci.yml`, as a workflow-level variable that both the toolchain step and the cache key read.
- [x] `Swatinem/rust-cache` sees only the pinned toolchain: a step removes every other toolchain the runner image ships before the cache is restored, so a toolchain bump still starts a new cache. Changed from `add-rust-environment-hash-key: false`; see the comments.
- [x] The cache is saved only on `refs/heads/main` (`save-if`).
- [x] The concurrency group is per commit on `main` and per ref on pull requests, with `cancel-in-progress` on for pull requests only. Done in `82d7f2c`.
- [x] Proven from the run history: two pushes to `main` a few seconds apart both run to the end, side by side, neither cancelled nor waiting on the other.
- [ ] Proven both ways. A push that changes only documentation restores with `full match: true` on both jobs. A push that bumps the toolchain misses, as it must. The first half is proven; the second waits for the next toolchain bump (see the comments).
- [x] ADR 0021 records how CI works: free standard runners, pushes straight to `main`, the full suite on every push with no selection, a run of its own for every push to `main`, the pre-push hook as the gate, and the time budgets. Each decision carries its reason from the spec. `documentation/README.md` gains its row.
- [x] The comments below record before and after by run ID: cache hits and the time of each job.

## Notes

- The image rollout that broke the key is in the spec: run 44829533423, attempt 1 on image `20261102` and attempt 2 on `20261117`, with keys `688f0a87` and `60948658` for the same commit.
- `CARGO_INCREMENTAL=0` stays as `rust-cache` sets it. Incremental artifacts would make the cache larger without speeding up a clean CI build.

## Comments

- **Concurrency, proven on 2026-11-21.** Run 44840700119 (`6a70891`) ran from 23:59:13 to 00:00:45Z. Run 44840781257 (`e3c4f7e`) ran from 23:59:58 to 00:01:45Z. They overlapped, both succeeded, and neither was cancelled or waited on the other.
- **The warm baseline, before the cache fix.** Both runs got the same macOS image, so all four restores were full matches (Linux key `2fd77104-b9b02d95`, macOS key `60948658-b9b02d95`). From push to result they took 1 min 32 s and 1 min 47 s. The Linux job took 36 s and 29 s, the macOS job 89 s and 105 s. This is what every push should look like. Until this ticket lands, it holds only while GitHub hands out the same macOS image.
- **Why the toolchains are removed instead of the hash turned off, 2026-11-20.** In `rust-cache` v2 (`src/config.ts`), `add-rust-environment-hash-key: false` drops two hashes, not one: the environment hash, which holds the installed toolchains, and the hash of `Cargo.lock` and every `Cargo.toml`. With it off, the key would never change when a dependency does. The old cache would restore as a full match, `rust-cache` skips saving on a full match, and every later run would rebuild the changed crates. Instead, `.github/actions/rust/action.yml` installs the pinned toolchain, removes every other one, and restores the cache. Both hashes stay. The pinned version reaches the key twice: through `rustc -vV` and through `RUST_TOOLCHAIN`, which `rust-cache` hashes because it starts with `RUST`. Run 44829533423 shows the cause in its logs. On image `20261102.0473.1` the environment considered `1.100.0` and `1.99.1`, giving restore key `v0-rust-macos-Darwin-arm64-688f0a87`. On `20261117.0516.1` it considered only `1.100.0`, giving `v0-rust-macos-Darwin-arm64-60948658`. The lockfile part, `a251ba0f`, was the same in both. The three jobs share the action, so the toolchain and cache steps are written once.
- **After, measured on 2026-11-21.** Every run below is a push to `main`. The Linux job got image `ubuntu-26.04` `20261116.202.1` each time.

  - The first run missed on purpose: the environment hash changed, because `RUST_TOOLCHAIN` became a variable and the extra toolchains were gone. It saved `v0-rust-linux-Linux-x64-2d41c47d-b9b02d95` and `v0-rust-macos-Darwin-arm64-b9070055-b9b02d95`.
  - **The bug is fixed.** Run 44845110942's macOS job landed on image `20261102.0473.1`, the one that ships Rust 1.99.1 as `stable`. The step removed `stable-aarch64-apple-darwin`, and the job restored `b9070055` with a full match, the same key the `20261117` image produces. Before this ticket, those two images gave `688f0a87` and `60948658`.
  - Every job removed the image's `stable` toolchain. Installing and cleaning the toolchain, plus restoring the cache, took 14 s on Linux and 26 s on macOS when warm.
  - Run 44845164171 is the documentation-only proof: full match on both jobs.
  - **Still to prove: a toolchain bump misses.** The pinned version reaches the key through `rustc -vV` and through `RUST_TOOLCHAIN`, and run 44844344492 shows that a change to the environment hash misses. A real bump is the proof the ticket asks for. It comes with the next stable Rust, or sooner with a throwaway pull request that changes `RUST_TOOLCHAIN`, which reads the cache and never writes it. The owner decides whether a pull request is worth opening.
