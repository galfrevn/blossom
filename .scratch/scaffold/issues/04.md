# 04: First run: the app opens the local board

**What to build:** with `vb serve` running, the operator opens Blossom and sees which board is open, by its address, and who they are on it, by the handle and name the board gives them. With no board running, they see how to start one. Nothing has to be configured. This is the first run of ADR 0012, without the field to paste another address.

**Blocked by:** 02

**Status:** ready-for-agent

- [ ] A `blossom` core crate with no dependency on Tauri. It reads the files in `board/local` under `$XDG_CONFIG_HOME`, or under `~/.config` when that is unset, on macOS too. The folder's location is a parameter.
- [ ] Only a file whose URL is on loopback is a candidate. A candidate is a local board only when discovery answers at its URL and names that same URL.
- [ ] For the board it opens, the core calls `/me` with the file's token, and shows the handle and name from that answer. A refused token means the board cannot be opened.
- [ ] With several local boards, the one whose file was written most recently opens.
- [ ] The contract has one subscription, the open board. Its value is "no board" or the board's URL with the person's handle and name. It never carries the token.
- [ ] The TypeScript types are generated from the Rust types into a single file with no header comment, and `check` fails when that file is stale.
- [ ] The desktop shell forwards the subscription over a Tauri IPC channel, under a capability that grants only that.
- [ ] The UI reaches the core through one client module with two implementations, Tauri's and a fake core. The open board lives in a store outside React, read with `useSyncExternalStore`.
- [ ] Two screens, "no board running" and "board open", with every string in the typed English dictionary.
- [ ] Core tests come first and drive the subscription with a temporary folder and a real local HTTP server. They cover no folder, an empty folder, one board, a board that does not answer, discovery naming another URL, a non-loopback URL, a refused token, and two boards.
- [ ] UI tests come first and render the app against the fake core, asserting what a person sees on each screen.
- [ ] Verified by hand against a real `vb serve`. The size the HTTP client adds is written down in this ticket.
