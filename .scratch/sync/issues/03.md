# 03: Resume after a restart

**What to build:** reopening the app on a board it has copied before resumes the feed from the replica's stored cursor, without copying again, so the board is ready at once. A cursor the board no longer accepts starts a new copy. A different board running at the same address, such as another project's `vb serve` on the same port, gets a replica of its own instead of being mixed into the old one.

**Blocked by:** 02

**Status:** ready-for-agent

- [x] A board's identity is its address plus the creation time and ID of its oldest message, and its replica is named after it.
- [x] Opening a known board follows the feed from the stored cursor; a 400 `invalid_cursor` replaces the replica with a fresh copy.
- [x] Tests come first: a restart resumes without copying; a refused cursor copies again; a different board at the same address gets a new replica.
- [x] Verified by hand: restarting the app on the 100,000-message board does not copy it again.

## Comments

From ticket 02, 2026-11-20: the replica now stores its feed cursor with every batch, and the copy stores its last one. Until this ticket lands, a restarted `vb serve` is copied whole again, because it mints a new token and the app starts over with it.

Built on 2026-11-21, test-first. The core gained 8 tests (the sync 5, the replica 3, replacing the old naming test).

**Verified by hand** against `vb serve` holding 100,062 messages:

- **The app's first launch** copied the board and named its replica after it in 8.3 s: `http---127-0-0-1-4200-api-board.2026-11-21t00-21-31-398z.2.sqlite`.
- **Quit, a message posted while it was closed, reopened.** One second after launch the status bar already read "100,063 messages", the missed message included, with no copy. The core on its own resumed and caught up in 65 ms.
- **`vb serve` restarted cleanly, minting a new token.** Two seconds after it was back, the app read "100,064 messages" without copying, and a post arrived.

Decisions made along the way:

- **A replica's file is `<address>.<oldest message's creation>.<its id>.sqlite`,** and the replica keeps that identity inside as well. The dots keep one address's files apart from another's, whose names never contain one.
- **A copy is written to `<address>.new.sqlite` and renamed after its board once it is whole,** so a file named after a board always holds a finished copy. An unfinished one, left by quitting during a copy, is thrown away when the next copy starts.
- **Recognizing a board takes one request,** `GET /messages/<oldest id>?limit=1`, compared against the stored creation time. Finding the oldest message again would mean reading every thread. A board that answers 404, or a different creation time, is a different board. A board that does not answer is waited for with the usual pauses, and can turn out gone.
- **A board that was empty when copied has nothing to be recognized by,** so it is copied again on the next start. That copy is small by definition, unless the board filled up while Blossom watched it.
- **A cursor refused with `400 invalid_cursor` throws the replica away and copies again,** once; a cursor refused right after a fresh copy stops with "Stopped: can't read the board" instead of copying in a loop. A local board answers `invalid_cursor` only for a cursor that isn't a number. A number past its end starts from the end instead, which is why the identity check comes first.
- **Replicas from before this ticket, named only by address, are left where they are and ignored,** since they hold no identity. No release has shipped, so there is nothing to migrate.
