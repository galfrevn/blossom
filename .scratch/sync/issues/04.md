# 04: Notice a board that died

**What to build:** when the open board stops answering its feed and its discovery, the app shows "No board running", even if the board's token file was left behind. The replica stays on disk. This closes the case ticket 05 of the scaffold left out of scope.

**Blocked by:** 02

**Status:** ready-for-agent

- [x] When reconnecting keeps failing and discovery no longer answers, the core reports the board gone, and the open board becomes "none running".
- [x] A board that comes back at the same address is opened again by the follower, as before.
- [x] Tests come first: a fake board that stops answering is reported gone, and its replica is kept.
- [x] Verified by hand: killing `vb serve` without letting it remove its token file returns the app to "No board running".

## Comments

From ticket 02, 2026-11-20:

- A board killed with `kill -9` already shows "Reconnecting", and a restarted one is found again through its rewritten token file. What remains is telling a board that is gone from one that is slow.
- A fatal error in the copy or the feed, such as an event the core cannot read or a replica it cannot write, stops that work and leaves the last state on screen. This ticket should decide what the status bar says then.

Built on 2026-11-20, test-first. The core gained 9 tests (the sync 7, the open board's follower 2) and the UI 2. Each of the two fixes found by hand was checked by breaking it and watching its test fail.

**Verified by hand** against `vb serve` holding 100,060 messages:

- **Killed with `kill -9`, leaving its token file.** The status bar said "Reconnecting" at 2 s and "No board running" at 3 s. Restarted, the board was opened and copied again, and a post arrived.
- **Frozen with `SIGSTOP`.** "Reconnecting" by 60 s and "No board running" by 90 s. Thawed, it was opened again on its own: live at 100,061, with a post arriving in 1.1 s.
- In one early run the app still said "Reconnecting" 8 s after `kill -9`. Three later runs, and the core run on its own, all turned at 3 s, so it was not reproduced. Whatever held it, a socket that neither answers nor refuses now ends within about 70 s, as the frozen board does.

Decisions made along the way:

- **A board is gone after three failed attempts in a row, when it then no longer answers discovery and `/me` with the same token,** the check that opens a board. A board that refuses its feed but still answers is never called gone, and a test covers it.
- **The core has one entry point, `keep_in_step`.** It opens the replica, copies the board and follows it, and ends either with the board gone or stopped. The shell only learns how it ended.
- **A gone board makes the follower forget the open board,** so its next look starts over: "No board running" if nothing answers, or the board again if it came back. The replica stays on disk.
- **A fatal error is now a state.** The status bar says "Stopped: can't read the board" for an event or page the core cannot read, and "Stopped: can't write the replica" when the replica cannot be opened or written. Nothing retries it; restarting the app does.
- **A stream that ends in an error counts as a failure,** whether 45 s of silence or a reset; only the board's own close is healthy. **Opening a stream waits at most 10 s.** Found by freezing `vb serve`: the app went on saying "100,059 messages" for 45 s, and would have taken about 3 minutes to say the board was gone.
- **The pacing's timings are named fields,** so a test can shorten any of them.
- **Fake boards that die are bare `wiremock` servers.** Pooled ones keep listening after they are dropped, and another test could have brought a dead board back.
