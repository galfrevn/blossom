# 03: Commands in the finder

**What to build:** the finder lists commands alongside results: open each lens, choose a channel, open the shortcut sheet, and every action the app has, each with its shortcut. Commands are declared once and the finder, the shortcuts and the sheet read the same list.

**Blocked by:** 02

**Status:** ready-for-agent

- [x] One list of commands, each with a title in the dictionary, a shortcut and what it does.
- [x] Commands match what is typed, before results when they match well.
- [x] Tests come first, against the fake core.

## Comments

Built on 2026-11-23 by a subagent in its own worktree, test-first, on `main` at a774862. The UI gained 23 tests and went from 245 to 268.

**What was built.**

- **One list of commands**, `ui/commands.ts`. Each command has a title from the dictionary, a group, the shortcut that does the same thing, and what it does. The application builds the list from the choice on screen, and the finder reads it; Search 04's shortcuts and sheet are to read the same list.
- **The lenses are listed once**, in `ui/frame/lenses.ts` (lens, name and key). The sidebar reads it, keeping each lens's icon in a map typed by lens, and the commands derive "Go to …" from it, so a lens added there gets its command with its key.
- **The commands today:** "Go to Flow" (2) and "Go to Tasks" (3), and, while a channel is chosen, "Show the whole board", whose shortcut is the key of the lens on screen, since pressing it again already widens. Going to a lens from the finder never widens the one on screen (`showLens`), unlike the sidebar's key pressed twice.
- **Matching** (`ui/finder/matching.ts`): a command matches when every word typed starts a word of its title, which is a good match and comes before what the search found, or appears inside one, which comes after. Case does not matter, the quotes of the search's phrases are ignored, and the words typed are marked as in the results.
- **In the finder** (`ui/finder/finding.ts`, which took the dialog's state and kept `dialog.tsx` under 300 lines): with nothing typed it lists every command, as the concept does. The commands follow each key at once, without the core; what the search finds joins them when it answers. A command reads as its title with its shortcut beside it, under "Lenses" or "Actions" as the concept groups them, and Enter or a click runs it and closes the finder.
- **The box says what the concept says:** "Search or run a command", the query "Go to a lens, find a task, or run a command", and "↵ run" in the foot.

Decisions made along the way:

- **A channel is chosen through what the search finds,** not through one command per channel. The core already ranks and marks channels, and a board of hundreds of channels would list them all as commands.
- **No command opens the shortcut sheet yet.** The sheet comes with Search 04, and a command that opens nothing would be a stub; Search 04 adds it to the list with `?`.
- **The rest of the app's actions join as they are built.** The concept's palette lists the lenses and the app's own actions: start a thread and create a task (the writing spec), everyone's attention (Attention), and switching boards (Boards). Each adds its command to the same list. The controls inside a lens, such as Tasks' state chips and title filter, stay in the lens, where the concept draws them.
- **"Go to Flow" is listed while Flow is on screen,** as the sidebar lists it; running it only closes the finder.

**Verified** in a headless browser against the built UI, with the answers the replica gave in Search 02, in dark and light: the commands with nothing typed, "Show the whole board" while narrowed, "low" marking "Go to F**low**", and the search's results with no command matching. The app itself was not run: this ticket has no hand verification, and the finder's searching is as Search 02 measured it.
