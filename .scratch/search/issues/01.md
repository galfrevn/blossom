# 01: The replica keeps a full-text index

**What to build:** the replica keeps an FTS5 index of every message's text, in the same transaction as its view, and answers ranked results with marked snippets: messages, tasks, channels and agents, at most 50 each. An existing replica builds its index once when it opens.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [x] Prefixes and quoted phrases match; an edit and a deletion change what matches.
- [x] The contract gains the search request.
- [x] Tests come first, against a real SQLite replica.
- [x] Measured on the 100,000-message replica: a query in under 50 ms, and the file's growth written in the ticket's comments.

## Comments

Built on 2026-11-21 by a subagent in its own worktree, test-first, and integrated onto Flow 04, Thread 01 and Fleet 01. The search suite has 23 tests, and the replica suite gained 1.

- **Four FTS5 indexes kept by triggers** in the transaction that stores the views: `message_words` (every message's text, read through the view `searchable_messages`, with no copy of the text), `task_words` (task roots), `channel_words` and `agent_words`. An edit re-indexes only when `text` or `deleted` changed; a deleted message is indexed with no text.
- **The reader** answers all four groups from one snapshot, at most 50 results each, with 12-word snippets whose marks travel as `{ text, marked }` parts, never as HTML. Every word matches as a prefix, closed quotes match a phrase, an unclosed quote is a phrase still being typed, FTS5's syntax is read as plain words, and accents do not matter.
- **Only the newest 10,000 matches are ranked:** ranking costs about 1.2 µs a match, and a word found on all 100,000 messages took 140 ms to rank.
- **The schema** moves to version 5 with the merge, so a replica from before is copied again. The spec asked for building the index in place (about 0.5 s); copying again costs a whole first copy. If that matters, it is a decision for an ADR.
- **Measured by the subagent** on the 100,000-message board's views: the slowest query 26 ms (a phrase still being typed), common words 13 to 22 ms, rare words under 0.4 ms. The file grew by 7.7 MB (7%). Storing the 100,000 views took 4.4 s with the index, against 2.3 to 2.6 s without it.
- **Verified by hand in the app** on the 100,000-message board: every group answers (50 messages for common words, one for a message's number, 11 channels for `area1`, 40 agents for `agent`). The times were taken while three other sessions were compiling (load average 44): rare words took 2 to 4 ms, common words 84 to 133 ms at the median. They are to be measured again on a quiet machine, with Release 01's budget command.
- **Measured again on a quiet machine** on 2026-11-21, at `main` 2338cc3, release build, load average 1.6 to 1.9, against a fresh `vb serve` holding the same 100,070 messages. Release 01's budget command does not exist yet, so the times come from the page, through the same harness as before: each query asked 10 times through the shell's `search` command, counted from the page.
