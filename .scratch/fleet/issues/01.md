# 01: The core knows each agent

**What to build:** the core answers the fleet: every agent the replica has seen, with the person it acts for, the task it holds and its lease, whether its lease lapsed, whether it failed recently, and its latest channel. It follows the replica.

**Blocked by:** Tasks 01

**Status:** ready-for-agent

- [x] An agent is an actor of kind `agent`; people are left out.
- [x] Lapsed means its latest claim ended in `task.expired`, or its `until` has passed while the board says claimed; failed recently means a task it held failed in the last hour.
- [x] The contract gains the fleet's subscription.
- [x] Tests come first, against the fake board's history.

## Comments

Built on 2026-11-21 by a subagent in its own worktree, test-first, and integrated onto Flow 04 and Thread 01. The core gained 19 tests: 12 for the fleet against the fake board's history, across a copy and a live follow, and 7 for board time.

**What was built.**

- `ReplicaReader::fleet(now)` returns every agent the replica has seen, ordered by handle so each person's agents sit together. "Now" is a board-time string, so tests pass fixed times; the shell makes it with `blossom::time::board_time(SystemTime::now())`, plain Rust with no new dependency.
- The schema gains three indexes: `messages_by_author`, `tasks_by_claim` and `task_events_by_actor`. It reads `messages.author`, which Flow 04 stores as the author's actor ID. Merged onto Flow 04 and Thread 01, the schema is version 4.
- The shell's `Session` gains a `watch` channel and `subscribe_to_fleet`. It sends the fleet only when it changed, after every stored batch, and reads it again once a second.

**Verified by hand** on `vb serve` with two agent profiles: subscribing answered both 26 ms later. codex held the task it had just claimed, with its `until`, in `#fleet/api`. claude read as lapsed: its claim, an hour old, had run past the 15 minutes `vb serve` gives a lease.

**Measured** with a throwaway test, release build, on 1,000 agents, 100,000 messages, 10,000 tasks and 30,000 task events: a fleet read takes 7 ms (median 6.6 to 7.0 ms, worst 7.6 ms), with every lookup an index seek, and 0.4 ms at 100 agents. Storing the 100,000 messages took 3.6 s with the new indexes, against 2.4 to 3.4 s without them; the runs were noisy.

Decisions the spec did not settle:

- **What an agent holds:** when it holds more than one claim, the one whose lease ends last.
- **Expiry is matched by the claim's epoch.** `task.expired` carries `id` and `epoch`, not `by`, so "the latest claim ended in `task.expired`" means an expiry on that task, after the claim, with the same epoch.
- **A failure belongs to the actor of `task.failed`.** Board only lets the claim fail a task, so that actor is the agent that held it.
- **Lapsed lasts until the agent claims again,** as the spec's "its latest claim" implies.
- **Channel:** the later of the agent's latest message and its latest claim; a tie goes to the claim.
- **A once-a-second read in the shell.** Without it, a lease that ran out on a quiet board would never read as lapsed, because Board's hosted backend appends no `task.expired`, which is exactly what happens when an agent crashes. It costs one 7 ms read a second at 1,000 agents.

**Left for sync:** the copy and the feed read `/events` without `all=true`, and Board counts `task.renewed` as bookkeeping, so renewals never reach the replica and a claim keeps its first `until`. On a hosted board, where a lease lasts at most five minutes, an agent that renews would read as lapsed after its first lease. It is sync's ticket 05.
