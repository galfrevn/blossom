# 02: Markdown and code blocks

**What to build:** a message's text renders as markdown, with headings, lists, emphasis, links, tables, quotes and inline code, and its code blocks keep their spacing and show their language. Raw HTML renders as text.

**Blocked by:** 01

**Status:** ready-for-agent

- [x] A markdown lexer is chosen against ADR 0009's JavaScript budget, and its weight is written in the ticket's comments.
- [x] Tokens become React elements; nothing goes through `innerHTML`.
- [x] Links open in the default browser on a click.
- [x] Tests come first: each construct, and messages that try raw HTML and scripts.
- [x] `bun run check` passes, with the JavaScript budget.

## Comments

Built on 2026-11-21 by a subagent in its own worktree, test-first, finishing the work of one interrupted when the machine shut down, and rebased onto Fleet 01 and Search 01. The UI gained 57 tests: 51 for the markdown (blocks 25, inline 17, nesting 6, links 3), 4 in the pane for links, and a message's own file of 6, which took over the pane's 4 tests of a message. The desktop shell gained its first 8 (links 4, navigation 4).

**The lexer is marked 18.2.1's**, the expected fit. Only its `Lexer` runs: `ui/markdown` turns its tokens into React elements, and its parser and renderer are never called. The UI's JavaScript went from 76.6 KB to 93.4 KB gzipped, of the 250 KB budget. That is 16.8 KB with the markdown module, about 4 KB over the spec's estimate, because marked's bundle does not tree-shake: importing only the lexer still brings the parser and the renderer (a bundle of the lexer alone weighs 15.4 KB). ADR 0009's table still says 70 KB.

**Verified by hand** against `vb serve` 0.54.0, in the release app run with a home of its own, on a thread holding a report (headings, numbered and nested lists, a task list, emphasis, strikethrough, inline code, a link with a title, a table with three alignments, a quote, a rule, bare addresses and an email), code (a `ts` fence, a fence with no language holding a long `ENOENT` line and a stack trace, an indented block), hostile HTML (a fixed red `div` over the page, `<script>`, `<img onerror>`, an HTML link, `<style>`, `<iframe>`, `<details>`, `javascript:`, `file:` and `data:` links, an image, character references, a mention, escapes), a message of 9,990 `>`, and a person's reply with a link:

- Everything read as the concept draws it, in dark and in light. The HTML read as text and nothing ran or moved. The deep message drew eight quotes and the rest as written. A reply posted while the pane was open arrived with its link.
- A click on a link opened it in Chrome, the default browser, and the window stayed on its page. A middle-click on the same link tried to take the window there, and the shell refused it: `blossom: the window stayed on its page instead of going to http://127.0.0.1:4500/?from=blossom-thread-02`.

Decisions made along the way:

- **GitHub's flavour, with its line breaks.** `gfm` and `breaks` are on: tables, task lists, strikethrough and bare addresses work, and a single newline breaks the line, as in GitHub's comments.
- **Raw HTML reads as text.** An HTML block reads as a paragraph that keeps its line breaks, and a tag inside a line as the characters it is. Named character references (`&amp;`) read as written, as raw HTML does; marked decodes numbered ones (`&#169;`) itself.
- **Only `http`, `https` and `mailto` become links.** Anything else (`javascript:`, `data:`, `file:`, a path inside the app) reads as its text. The page checks the scheme, and the shell checks it again before it hands the address to `/usr/bin/open`, so no plugin and no dependency was added. A link shows its address on hover, since the webview has no status bar.
- **One click listener, on the pane.** Not one per link, and not on the pane's feed, which is drawn anew for every thread: a listener there lost the links at the first thread.
- **Nothing navigates the window.** A plugin in the shell (`desktop/src/navigation.rs`) keeps the window on its own page, or on the dev server while developing. The content security policy cannot do this, and the middle-click above shows it is needed.
- **An image in a message is a link named by its description.** Nothing loads by itself, as the content security policy and ADR 0013 want. Images inline come with attachments.
- **Headings start at `h3`,** under the pane's `h2`, and stop at `h6`.
- **Code blocks wrap their long lines, as the concept draws them,** rather than scrolling sideways. They keep their spacing, name their language (the fence's first word) in a caption, and their text can be selected. Wide tables scroll sideways.
- **Links are ink with an underline,** not pink: ADR 0016 keeps the accent off actions.
- **Nesting stops at eight levels,** with quotes, lists, emphasis and links counted together; the rest reads as written. A message of 10,000 `>` is 10,000 nested quotes, and drawing them overflowed the stack. If the lexer itself overflows, the message reads as written: V8 does at 10,000 quotes in the tests, JavaScriptCore did not in the app.
- **No memory of parsed messages,** which the interrupted subagent had started. Messages are memoized, so a re-read parses only what changed, and lexing is cheap in JavaScriptCore (bun, load average 2): 4 ms for 154 report-sized messages of 456 characters, 0.3 ms for 154 short ones. The worst cases are 76 ms for 154 messages of 10,000 characters, and 133 ms to lex one hostile list nested 300 deep.
- **A message's tests moved** from the pane's file to `ui/thread/tests/message.tsx`, beside `ui/thread/message.tsx`, which also keeps the pane's under Biome's 300 lines.

Left for later: a middle-click on a link does nothing, and Flow's lines still show a message's markdown as written.
