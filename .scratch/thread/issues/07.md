# 07: The pane opens at the message it was asked for

**What to build:** when the pane opens a thread for one of its messages, from the finder, a line in Flow or anything else that names a message, it scrolls to that message and marks it for a moment. Today it opens at the top, so a reply found deep in a long thread can be out of view (found in Search 02).

**Blocked by:** 01, Search 02

**Status:** ready-for-agent

- [x] The pane scrolls the message asked for into view once its thread is drawn, and marks it as the concept marks a selected line, then lets the mark fade.
- [x] Opening the root, or a thread whose messages all fit, leaves the pane at the top.
- [x] Tests come first, against the fake core.
- [x] Verified by hand on a thread of a few hundred replies, opened at a reply near its end from the finder.

## Comments

Built on 2026-11-23 by the integrator, test-first, on main at f9e09c8, without a subagent. The UI gained 9 tests: 7 for landing (`ui/thread/tests/landing.ts`), 1 in the pane and 1 for links; the pane's test of a click beside a link moved to the links' tests, which is where that behaviour now lives. Every new test failed first.

**What was built.**
- **The pane lands on the message it was asked for** (`ui/thread/landing.ts`). Once the thread holding that message is drawn, the pane scrolls the message to the middle of its body and marks it with the accent's wash, the colour Flow gives a selected line. The mark fades over a second after 1.6 s.
- **Only a new message asked for moves the pane.** The thread read again after a change, a reply arriving, or the reader scrolling leave it where the reader has it. Another message of the same thread asked for, from the finder or a line, moves it again.
- **The root leaves the pane at the top, unmarked,** as before. So does a thread whose messages all fit, since scrolling a message into view moves nothing there.
- **A message the drawn thread does not hold waits** for the read that holds it, so the pane never lands on the thread it is leaving.

**Verified by hand** against a `vb serve` 0.54.0 of my own on port 4500, with a thread of 300 replies by two agent profiles, and the release build under a home of its own. A temporary line in the page, not in this change, did what a person does: ⌘K, "step 290", Enter. It then read the pane: the reply was on screen inside the pane's body and marked, with the body scrolled to 17,399 px of 18,397. A second reading, meant to see the mark gone 2.6 s later, never came back; the window was behind others, and WebKit holds a hidden page's timers (Search 02). The fading is covered by a test with a fake clock.
